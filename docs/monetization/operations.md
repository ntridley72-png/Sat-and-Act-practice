# AdSense configuration and rollout

## Before requesting approval or enabling ads

Google alone decides approval; this repository cannot guarantee it. Keep `ADSENSE_ENABLED=false` until the account/site is approved and the checks below are complete. Never test using live impressions or click your own ads.

- Verify site ownership and original, useful content. Review generated score/college/scholarship/game pages individually for thin, repetitive, inaccurate or replicated content. Technical SEO passing is not an AdSense content-quality approval. The manager has a conservative 350-word editorial floor on content documents, excluding navigation/footer; this is a FunSAT heuristic, **not** a Google policy threshold or guarantee.
- Verify privacy/about/contact/methodology information and a private way to handle personal deletion requests. Do not put student personal information in public GitHub issues.
- Review the actual audience and any under-13/child-directed obligations with an appropriate qualified advisor. SAT audience does not prove every visitor's age. The former child-directed attribute is not a substitute for correct account, consent and age treatment. Set `ADSENSE_AUDIENCE_REVIEWED=true` only after configuring the applicable treatment in the publisher/CMP setup. No age or behavioral profiles were introduced.
- Set up a Google-certified CMP and the applicable GDPR/UK/Swiss and US-state messages. Use a separately loaded CMP bootstrap that works **before** the advertising script. The CMP itself must not depend on this manager's AdSense loader, which waits for consent. Connect the CMP's actual authorized advertising state to the API below. A custom “accept” button or a remembered boolean is not a certified CMP.
- Confirm the root interactive URL is excluded from **all** Auto Ads. Test exclusions live through the AdSense preview and policy center. Hash changes and SPA screen changes are not reliable URL exclusions. Do not mark confirmation before this is done.

## Worker configuration

Set these public values as Cloudflare Worker variables (dashboard Settings → Variables and Secrets, or a `[vars]` section in wrangler.toml). No IDs are spread through templates. Redeploy after changing configuration. Script reads use `no-store`.

| Variable | Value |
|---|---|
| ADSENSE_ENABLED | `true` only after rollout checks; otherwise `false` |
| ADSENSE_CLIENT | Your actual `ca-pub-` followed by 16 digits |
| ADSENSE_SLOTS | JSON map of placement name to the actual unit ID (string) |
| ADSENSE_APP_EXCLUDED | `true` only after all Auto Ads are excluded on the app URL |
| ADSENSE_AUDIENCE_REVIEWED | `true` only after audience/treatment review |
| ADSENSE_GAME_RAILS | `0`, `1` (initial), or `2` |
| ADSENSE_RESULTS_DENSITY | `conservative` (initial) or `moderate` |
| ADSENSE_VIGNETTE_MINUTES | `3`, `5`, or `10`: **reporting label only** |
| ADSENSE_EXPERIMENT | e.g. `baseline-3m-one-rail` |

Valid manual placement names: `home-sidebar`, `results-top`, `results-analysis`, `college-list`, `scholarships-list`, `subjects-list`, `article-mid`, `article-bottom`, `arcade-menu`, `game-left`, `game-right`. Only configure units you want to request. Game rails need **fixed 160×600 display units**; other names need standard responsive display units. Do not use fluid/in-feed IDs with this display implementation. `results-analysis` is available only with moderate density, after answer review is opened with at least 10 questions; it is never stacked immediately after the first results unit. Use distinct game rail IDs for reporting.

Example schema (replace with real IDs): `{"results-top":"YOUR_DISPLAY_UNIT_ID","article-bottom":"YOUR_DISPLAY_UNIT_ID","game-left":"YOUR_160x600_UNIT_ID"}`. Invalid or missing IDs leave slots hidden. `/ads.txt` is generated by the Worker from a valid publisher ID; check Google's account-specific authorized-seller instructions before adding any other seller. Static hosts must configure `ads-config.js` and their actual ads.txt independently.

## Consent and analytics adapters

From your certified CMP's documented callback, after **all applicable** advertising purpose/vendor, audience and regional requirements have passed:

```js
window.FunSatAds.setConsent(authorizedAdvertising === true);
```

Alternatively dispatch `new CustomEvent('funsat:ad-consent', {detail:{granted: authorizedAdvertising === true}})`. Call after `ads.js` is ready; if CMP finishes earlier, invoke the current state at readiness. On withdrawal call false to stop new manual requests and let the CMP execute its documented Google consent update/reload procedure. Removing a script cannot unload it or revoke previously delivered creatives. Do not modify Google-generated DOM. This project deliberately does not invent or infer consent from location or a TCF consent-string's mere presence.

Analytics is independently disabled until consent and a real collector are supplied:

```js
window.FunSatMetrics.configure({
  consent: authorizedAnalytics === true,
  send: (name, properties) => window.gtag('event', name, properties)
});
```

Use this only if GA is actually installed and consented. Another documented collector can replace `gtag`. Configure GA automatic/history pageviews consistently so FunSAT screen events are not double-counted. SPA screen events are **not AdSense pageviews**; use official AdSense pageview reporting for page RPM. No analytics library, tracking identifier, server collector, user ID, score, answer, email or ad-click listener was introduced. Event callbacks cannot block the product.

## Approximately three-minute vignettes — official controls

Current official instructions: [frequency](https://support.google.com/adsense/answer/13956167?hl=en), [vignettes/additional triggers](https://support.google.com/adsense/answer/16531962?hl=en), [Auto Ads settings](https://support.google.com/adsense/answer/9305577?hl=en).

1. Sign in to AdSense → **Ads**.
2. In the sites table, choose **Edit** next to `funsat.bid`.
3. Enable **Auto ads**.
4. Under **In-page formats**, enable **Banner ads** (the current in-page terminology). Start with conservative maximum density/minimum spacing and inspect the preview. Avoid overlapping manual units; initially leave “Allow Google to optimize existing ads” off to keep reviewed placements stable.
5. Under **Overlay formats**, enable **Anchor ads** and **Vignette ads**. Use Google's anchor placement controls; FunSAT has no custom anchor. Leave official side rails off on the interactive app; content-page side rails are a separate optional preview/review decision.
6. Under **Overlay formats → Advanced settings → Vignette ad frequency**, select **3 minutes**. Google's current documentation says the available range is 1 minute to 1 hour and the default is 10 minutes.
7. Keep **Allow additional triggers for vignette ads** enabled on eligible **content pages** if appropriate. These can include tab return and interaction after inactivity. They must not interrupt the interactive app, which is excluded.
8. Under **Excluded pages**, exclude the exact root URL `https://funsat.bid/` only, not every page under it. Include any alternative app-shell URL you actually serve. Also exclude privacy/contact/about/corrections/methodology, unsupported thin pages and interactive calculator pages where needed. Do not load Google code on content pages that fail the manager's editorial checks.
9. Inspect **Excluded areas** for article controls, navigation, calculators and other frequently clicked areas. These area exclusions alone do **not** disable vignettes.
10. **Apply to site** → apply/save, or use **Run experiment first** where offered. Changes may take time to propagate; verify on the live approved site without generating invalid traffic.
11. Set `ADSENSE_VIGNETTE_MINUTES=3` to match the setting for reporting. This variable does not change Google behavior.

Three minutes is eligibility, not a scheduled interruption. A 60-minute session does not imply 20 vignettes. No JavaScript ad timer, refresh, reload or fake navigation exists. Because the app shares one URL across active questions, games and results, vignettes are initially available on content documents **only**. To extend vignettes safely into game sessions requires a separately reviewed game document or approved H5 integration, not an attempt to hide an already served vignette.

## Experiments and sustainable revenue

Start at one safe game rail, conservative results, 3-minute content-page vignette eligibility. Configuration supports 0/1/2 rails and conservative/moderate results; the cohort label travels with consented product events. Google's frequency is controlled by AdSense, not browser cohort assignment. Use official Auto Ads experiments when that setting is supported, otherwise sequential 3/5/10-minute periods with matched weekdays and traffic mix. Do not claim simultaneous browser-controlled vignette arms.

Primary outcome: actual advertising revenue / active user and / session from the **same reporting interval**. Guardrails: completion/started rate, answered/served fraction, visible playing time, return rate, bounce, review engagement, satisfaction, mobile usability, LCP/CLS/INP. Suggested initial rollback triggers for investigation: >5% relative fall in SAT completion or return rate, >10% fall in visible playing duration, or mobile CWV moving out of the “good” range. These are operating proposals, not established FunSAT thresholds. Normalize consent, geography, device, seasonality and acquisition mix. Use two comparable weeks or enough sample size to assess uncertainty; do not infer success from a small revenue swing.

AdSense Reports supply actual revenue, pageviews, impressions, RPM and Active View metrics where available; FunSAT does not inspect cross-origin ad frames or fabricate viewability/revenue. No OAuth reporting credentials were supplied, so actual metrics can be entered manually in `model.html`; automatic reporting integration is not claimed.

## H5 Games findings

The 28 client-side canvas games are structurally HTML5 games and have natural game-over/round/menu states. Current official [game structure](https://developers.google.com/ad-placement/docs/html5-game-structure) and [API](https://developers.google.com/ad-placement/apis) documentation describes `adBreak`, `beforeAd` (pause/mute), `afterAd`, and `adBreakDone` (always called if supplied, including no-fill). This is distinct from ordinary AdSense content ads and requires publisher access/approval and the appropriate inventory setup. Repository access cannot establish your account's H5 eligibility or distribution/content rights.

No H5 requests or reward ads are enabled. The centralized loader and arcade manager are the integration boundary for a future **approved** H5 rollout; do not add another adsbygoogle script or generic display ad over a game. After account eligibility is confirmed, integrate only real round/level/game-over transitions, suspend input/game/audio in official callbacks, continue immediately on no-fill, and keep Auto Ads excluded to avoid competing fullscreen formats. Existing practice-earned credits are never tied to ad clicks or views. Active gameplay is never interrupted by a three-minute timer.
