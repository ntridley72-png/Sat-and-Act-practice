## 3–5. Existing code and replacement architecture

Active Adsterra scripts at bauval.org were hard-coded in the main HTML and Python generator. The old manager also supported direct sponsors/AdSense, moved one native unit among slots, loaded sandboxed third-party units, contained grid/anchor logic, and forcibly hid Google ads/vignettes during tests. Global rails were fixed at a 1420px media query. ads.txt had no authorized sellers. No publisher ID, CMP, aggregate analytics collector or admin dashboard was configured.

New `FunSatAds` is a single guarded manager: validated Worker config → audience/exclusion/consent gates → eligible/reserved host → viewport IntersectionObserver → one async official loader → one push per host. Returning to the same SPA slot does not refresh it. Failed/blocked loads preserve the product and reserved layout; no-fill cannot remove important content. Local `?adpreview=1` produces explicit development placeholders only. No live Google code loads on local/test hosts. Long substantive content can receive Google-controlled Auto Ads; short/legal/support pages remain disabled by the manager's editorial gate. No generated Google DOM is hidden or restyled.

## 6–11. Placement and experience map

| Area | Placement | Deliberate exclusions / behavior |
|---|---|---|
| SAT home/setup | `home-sidebar` | One separated responsive unit, no control-ad camouflage |
| Active question and adaptive transition | None | No ads in question, choices, timer, calculator or navigation; transitions remain ad-free because the test state shares its container/URL |
| SAT break | None | No break state existed; no fake state/page added |
| Completed results | `results-top` after actual scores/domain content | One responsive unit; score estimation and scoring preserved |
| Detailed results | `results-analysis` | Optional second responsive unit only after a genuine review of at least 10 questions; moderate configuration only |
| Answer review | Adjacent results inventory only | At most one optional unit at the end of a substantive review, none between questions/choices/explanations; all/missed/correct filters and end marker support meaningful review |
| College/scholarship/subject tools | One bottom `*-list` slot per screen | No stacked grids, overlays or units beside thumb-heavy filters |
| Arcade menu | `arcade-menu` after menu tiles/time bank | Separated responsive placement; no pre-roll barrier |
| Active desktop game | `game-left`, `game-right` | Fixed-size 160×600 display units in unused document-space; default one, optional two, no game scaling for ads |
| Study/college articles | `article-bottom`; optional `article-mid` after 8 paragraphs | Responsive and lazy; short/support/legal content stays ad-free; editorial review still necessary |
| Eligible content Auto Ads | Google's in-page, anchor, vignette formats | Google controls serving; root app excluded before enabling manual SPA inventory |

Rail geometry includes canvas, buttons, selects, D-pad and arcade HUD. A conservative bounding rectangle must be at least 150px from every visible interactive rectangle and fit with page margins. Width alone is insufficient. Below 1200px all side rails are disabled; larger screens can still have zero rails if the fitted game/controls consume the available space. A second rail appears only if separately safe and configured. Resizing removes unsafe rails; the game retains its original fitting algorithm. Mobile/tablet use no game side rails and no ad overlays over game controls. No custom sticky manual advertisements, ad grids, power-up ads, answer-like ads, or click/view rewards exist.

## 12–15. H5, vignettes and required publisher setup

HTML5/canvas structure is compatible in principle with the official H5 API, but account approval, supported inventory and rights cannot be established from source code. H5 is therefore not activated; no unfinished runtime H5 stub is shipped. The operations guide records official callback requirements and the integration boundary.

Vignette serving uses **Google's Auto Ads dashboard only**. No refresh/timer/fake navigation exists. The shared SPA URL prevents reliably excluding only active questions; therefore all Auto Ads are excluded from the app and vignettes initially monetize substantive content documents. This is the compliant alternative to hiding a Google vignette after it appears. Google’s additional triggers include tab return and inactivity followed by interaction; enabling those on the shared interactive root would be disruptive.

Exact initial steps: AdSense → **Ads** → site **Edit** → **Auto ads ON** → **In-page formats: Banner ads ON** → **Overlay formats: Anchor ads ON, Vignette ads ON** → **Advanced settings: Vignette ad frequency = 3 minutes** and additional triggers enabled on eligible content → configure **Excluded pages** for root app/support/unsafe tool pages → **Apply to site** / save or official experiment. Full instructions and current official links are in `operations.md`. `ADSENSE_VIGNETTE_MINUTES` only labels analytics; it does not set frequency.

Still required: real `ca-pub-…` publisher ID, responsive unit IDs and separate 160×600 rail IDs; site/account approval; consent bootstrap/authorized callbacks; correct audience treatment; confirmed Auto Ads exclusions; optional consented analytics property/collector. Actual reporting requires official exports/manual entry or a future securely authenticated AdSense reporting integration. No reporting credentials were supplied.

## 16–17. Analytics and experiments

Events wired: `sat_test_started`, `sat_module_completed`, `sat_test_completed`, `sat_results_viewed`, `sat_score_breakdown_viewed`, `sat_answer_review_started`, `sat_answer_review_completed`, `practice_started`, `game_started`, `game_round_completed`, `game_session_10min`, `game_session_30min`, `game_session_60min`, `game_session_ended`, `college_tool_used`, and deduplicated screen `page_view`. No SAT-break event is fabricated because no break exists. Review-completed means the end-of-review marker was reached, not proof every explanation was studied. Long-game milestones count visible playing time across rounds in one arcade visit, not idle-tab elapsed time. Existing credit/run limits are unchanged.

Analytics is disabled until an independently consented collector is configured. Safe event properties include counts, section/test type, game key, duration and experiment labels; never personal IDs, answers, scores or email. Gameplay continues if the sink throws. Product screen events are not official AdSense impressions or pageviews.

Configuration supports one/two rails and conservative/moderate results; experiment identifiers can label controlled deployments. Frequency comparisons must use Google’s supported experiment controls or properly matched sequential periods. Browser code cannot assign Google frequency per user. Initial configuration: 3-minute content-page eligibility, one safe rail, conservative results.

## 18–19. Performance, compliance and validation

No ad library is downloaded until permitted; no synchronous third-party loader, general DOM-scanning mutation observer (only dedicated game-control panels are observed), or ad refresh loop. IntersectionObserver requests units only when at least 50% of the reserved host is visible, avoiding far-below-fold requests. Reserved 300px responsive host height and 640px rail host height protect layout; blank no-fill space remains stable. Missing IDs create no blank production hosts. CMP arrival can reveal configured space during user interaction; real-network creative behavior and field CWV still need measurement. No actual LCP/INP/RPM uplift is claimed.

Policy findings: unsafe fixed rails, aggressive grid stacking, incorrect privacy/network description and forced hiding of Google-generated units were removed. Current Google documentation strongly recommends at least 150px from game edges; larger distance can be needed. Pure navigation/alert/empty-transition screens are not monetized. The retained content generator requires editorial quality review; technical checks cannot guarantee originality, inventory value, invalid-traffic safety or approval. Age/privacy obligations must be resolved before enabling.

Validated: full Python/Cloudflare asset build; 663-page SEO audit; original question-bank/scoring/adaptive tests; college and tutor logic; account and tutor-history integrations on a local D1 instance; all 28 arcade games; driving/drift/dirt-bike behavior; theme/college/scholarship/subject UI; new responsive and mocked ads tests. Existing browser tests used Linux Chromium through a temporary runner adapter, because their committed paths target macOS. Tests generated no live ad traffic. The live Groq-model probe was invoked against the local Worker; all model probes returned 403 forbidden because Wrangler rewrote the local Origin to http://funsat.bid, which the existing HTTPS-only production origin allowance rejects. No production endpoint was probed. This is an environment/test-origin limitation, not an advertising regression. No deployment or real AdSense account test was performed.

New tests cover mobile 390×844, tablet 768×1024, laptop 1366×900, desktop 1920×1080, and large desktop 2560×1440; rail clearance/removal; SAT completion/results/review; missing setup; consent; one script/push; simulated blocked loader/no-fill behavior. No console/page errors on the tested flows. Browser tests cannot prove actual Google fill, approval, revenue or field Core Web Vitals.

## 20. Next experiment and estimated business effects

First compare one vs two **safe** game rails on sufficiently wide desktops while keeping results and Google frequency unchanged. Measure official revenue/user and revenue/session alongside visible playing duration, return rate and SAT completion. After a stable baseline, compare 3/5/10-minute content-page eligibility with matched traffic or official experiments. Avoid changing several factors together.

| Metric | Expected mechanism and limits |
|---|---|
| Pageviews/user | Review filters improve study usefulness within the same page; they do not manufacture pageviews. Genuine content/game selection navigation may increase exploration, but uplift is unmeasured. |
| Ad impressions/session | Zero when consent/setup/inventory is absent; up to one request per eligible manual host per document, including one/two safe rails. Auto Ads delivery is Google-controlled; no duration-to-impression formula. |
| Viewability | Requests begin when at least half the reserved host is in viewport; safe visible desktop whitespace should improve opportunity to view. Official Active View reporting must confirm; iframe visibility is not measured as paid viewability. |
| Page RPM | Depends on geography, device, consent, advertiser demand and fill. No credible numeric forecast without baseline official data. |
| Session RPM | Revenue/session × 1,000; can improve with substantive exploration and actual eligible inventory, not elapsed-time refresh. |
| Revenue/user | Primary outcome; should be judged with completion/retention. No guaranteed uplift or earnings. |

Illustrative **model, not forecast**: at an assumed $10 page RPM, 3 official pageviews/user implies $0.03/user; 5 implies $0.05/user; 8 implies $0.08/user. At 10,000 users this is $300/$500/$800. For two sessions/user, $0.05/user corresponds to $0.025/session and $25 session RPM. These inputs must come from actual reporting before being interpreted as FunSAT earnings. A long game on one document can earn from genuinely viewed inventory, but does not inherently produce additional pageviews or repeated rail impressions.

The local model provides every requested user scenario (500–100,000), pageview choice (3/5/8/10/15), RPM ($5/$10/$15/$20), formula breakdown, and actual-revenue ratios once manually supplied.
